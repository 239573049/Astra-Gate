# Astra 插件系统 v2.0 设计

状态：**已按本设计实施 2.0 与 2.1**（2026-11-11）。「待确认」表里的决定都按「建议」一列实现（用户要求开始实施时没有另作决定）；以后改动其中一项，就是改已有代码，表和代码一起改。实现与文档不一致之处以代码为准。

v2 是一套全新的插件系统：新的清单、新的运行模型、新的能力 API、新的 UI API。它**不兼容 v1**（magpie 兼容层），
v1 插件继续按现状运行，但不再增加新能力。插件出了 v2 版本时，Astra 提醒用户升级。

## 目标

1. **一套 UI API，两端原生渲染。** 插件用 JS 描述界面，Web 控制台（React + arc 组件）和桌面端（Avalonia + TKCode.Arc）
   各自用原生组件渲染出同一棵树，外观和行为尽量一致。
2. **能力可扩展。** 新增一种插件能力（一个扩展点、一个宿主 API、一个 UI 组件、一个界面挂载位）是加一条注册，
   不是改加载器。
3. **默认安全。** 插件代码只在沙箱里跑，一切 I/O 经过宿主、受声明的权限约束。v2 插件不以用户权限运行任何进程。
4. **稳定的契约。** 清单、宿主调用、UI 树都是带版本的 JSON 契约，由同一份模式文件生成 TS 类型、C# 类型和文档。

## 非目标

- 不兼容 magpie / OpenCode / pi 插件的格式和名字（那是 v1 的职责）。
- 不提供 WebView / iframe / 任意 HTML 的界面方式（原因见 03 §11）。
- 不让插件直接访问文件系统、子进程、原始套接字。

## 核心设计一览

```
            ┌──────────────────────── astra-server (Native AOT) ────────────────────────┐
            │                                                                           │
 plugin.js ─┼─► 沙箱 (Jaunt)                    宿主                                     │
            │   ┌───────────────┐   宿主调用表    ┌──────────────────────────────────┐   │
            │   │ main 上下文    │◄──(JSON)─────► │ 扩展点注册表                      │   │
            │   │ 单例，串行     │                │  gateway.hooks / providers /     │   │
            │   │ UI·命令·任务   │                │  clients / ui.* / commands / …   │   │
            │   ├───────────────┤                │ 权限检查 · 限额 · 存储 · 网络      │   │
            │   │ gateway 上下文 │                └──────────────────────────────────┘   │
            │   │ 引擎池，无状态  │                         │ UI 树 / 补丁 / 效果          │
            │   └───────────────┘                         ▼                           │
            │                                    /api/plugins/v2/ui/*  (HTTP + SSE)    │
            └──────────────────────────────────────────┬────────────────────────────────┘
                                         ┌─────────────┴─────────────┐
                                    Web 渲染器                  Avalonia 渲染器
                                (React + arc 组件)            (TKCode.Arc 控件)
```

- **服务端驱动 UI**：插件的界面代码跑在服务端沙箱里，产出一棵 JSON 的 UI 树；两个壳各有一个渲染器，把节点类型映射到
  自己的 Arc 组件。桌面端不需要 JS 引擎，Web 端不执行插件代码。
- **两种执行上下文**：`main`（每个插件一个长寿命引擎，承载 UI、命令、后台任务）和 `gateway`（请求热路径上的引擎池）。
  两者不共享内存，只通过 `astra.storage` 和事件通信。
- **扩展点注册表**：插件在清单的 `contributes` 里静态声明贡献，宿主不运行代码就能知道插件提供什么；代码按需激活。
- **宿主调用表**：所有 `astra.*` API 都是「名字 + JSON 参数 → JSON 结果」的一次调用，经过同一个桥。权限、限额、
  审计都在这一个口子上做。

## 决定

### 已定

| # | 决定 | 结论 |
|---|---|---|
| — | v2 与 v1 的关系 | v2 全新设计，不兼容 v1；v1 保留支持；插件有 v2 版本时提醒用户更新（07） |
| — | UI 的方式 | 插件用 JS 构建界面，通过一套自定义的 UI API 同时支持 Web 和 Avalonia 桌面，尽量一致（03） |
| D10 | UI 1.0 的组件范围 | 完整词汇。树、日期、折线图、Markdown 是必须项，在 Web 的补齐顺序里排最前（04 §7、§12） |

### 待确认

文档按「建议」一列写成，2.0 也按它实现。改动一项时更新这张表、对应章节和代码。

| # | 决定 | 建议 | 备选 | 影响 |
|---|---|---|---|---|
| D1 | 插件 UI 代码在哪里运行 | **服务端沙箱**，两端只渲染 | Web 在浏览器里跑、桌面再嵌一个 JS 引擎 | 一致性、安全、桌面 AOT；代价是每次交互一次往返（03 §2） |
| D2 | v2 的运行时 | **只有沙箱（Jaunt）**，网络等 I/O 由宿主能力提供 | 同时保留 Bun 子进程运行时 | v2 是否还需要下载 Bun；依赖 Node API 的插件要重写（01 §3） |
| D3 | UI 写法 | **构建函数为基础**（不需要构建步骤），JSX 作为 SDK 的可选写法 | 只支持 JSX + 必须打包 | 上手门槛、SDK 工作量（03 §4） |
| D4 | 网关钩子看到的数据 | **两种都给**：原始协议体（`raw`）和协议无关的规范视图（`ir`） | 只给原始体（和 v1 一样） | `ir` 视图会成为公开契约，要单独定版本（02 §3） |
| D5 | 清单与分发 | 独立的 `astra.plugin.json`；分发以**市场 tarball** 为主，本地目录用于开发 | 继续用 `package.json` 字段 + npm | 是否还依赖 npm registry（01 §2、§9） |
| D6 | 权限授予 | 安装时由用户确认；升级时**只确认新增的权限**；可运行时申请 | 全部默认允许 | 安装体验、远程管理时的风险（01 §6） |
| D7 | v1 → v2 升级 | **提醒 + 用户确认后升级**，不自动 | 自动升级 | v2 有权限确认和数据迁移，自动升级会越过确认（07 §3） |
| D8 | 自定义绘制 | 提供 `Canvas`（矢量显示列表），不提供 WebView | 提供 WebView | 一致性与安全（03 §11） |
| D9 | 2.0 首版范围 | 运行时核心 + UI API + 网关钩子 + 设置表单 + 升级提醒；provider / client 扩展点放 2.1 | 一次做全 | 交付节奏（01 §11）；2.1 之前只有中间件类的 v1 插件会收到升级提醒 |
| D11 | 视图状态放在哪里 | **宿主持有 JSON 快照**，引擎可随时替换或卸载 | 留在引擎里 | 状态必须是 JSON 且有大小上限；换来超时不丢状态、空闲零占用、热重载保状态（03 §3.2） |
| D12 | 表格单元格、树节点的内容 | **有限的几种类型** | 任意节点 | 一致性与虚拟滚动；自由内容用 `List`（04 §6、§7） |
| D13 | Markdown 在哪里解析 | **宿主解析**成普通节点，两端只新增 `RichText` | 两端各用一个解析库 | 语法子集只有一份实现；解析器要在 Native AOT 下无警告（04 §7） |
| D14 | Web 端的折线图 | **手写 SVG**（和现有柱状图、迷你图一致），刻度算法写成两端共用的用例 | 引入图表库 | 包体积、和桌面的坐标轴是否一致（04 §7） |

## 待验证（动手实现前的技术验证）

这些是设计依赖、但还没在本仓库里证实的点：

1. Jaunt 的异步宿主函数（`JsEngine.SetAsyncFunction` / `InvokeAsync`，1.0.2 的 XML 文档里有）在 Native AOT 下的行为，
   以及一个长寿命引擎在大量 promise 往返后的 `TrackedBytes` 增长速度（它只增不减，见
   `.agents/memory/jaunt-replaces-jint.md`）。这决定 `main` 上下文多久需要换一次引擎。
2. 用 10 个左右组件做一个 UI 协议原型，两端渲染后用现有的视觉回归工具（`scripts/visual/`）比对，确认一致性的上限。
3. Avalonia 端按 key 复用控件的协调器，在补丁频繁到达时不触发「已有视觉父级」崩溃
   （`.agents/memory/desktop-rebuild-reparent-crash.md`）。
4. 远程管理（隧道）下 UI 事件往返的延迟是否可接受。
5. 每次事件序列化一次视图状态的开销（D11）：在 256 KB 上限附近，Jaunt 的 JSON 往返加上渲染能否保持在一帧左右。
6. 04 §12 的 Web 缺口清单是按 `web/src/components/arc/` 目录判断的；有些组件在页面里已有一次性实现，实际要新写的数量
   需要逐个确认后才能估工作量。
7. Markdown 解析器（D13）自己写固定子集还是用现成的库：取决于后者在 Native AOT 下是否无 IL 警告。
8. 市场注册表里 v2 条目的放置方式，要保证旧版本的 Astra 不会把它当成普通插件展示（07 §3.1）；动注册表之前定。
