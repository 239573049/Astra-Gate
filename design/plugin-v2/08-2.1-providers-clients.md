# 08 2.1：`providers`、`clients`、`ui.flows` 与流式 `net`

02 §12 只写了方向，这里是 2.1 的具体设计。原则：**复用 v1 已经铺好的接缝**，不另开一条请求路径。这样故障转移、
账号调度、代理、计费、隐私护栏、请求日志、令牌池全部照旧工作，v2 只换掉“背后是谁”。

## 1. 流式 `net`（已实现）

`http.fetch(url, { stream: true })` 在收到响应头时就返回，响应体留在宿主，按需读取：

| 接口 | 说明 |
|---|---|
| `res.stream()` | 字节块的异步迭代器（宿主调用 `http.read`，每次至多 64 KiB） |
| `res.lines()` | 整行文本（SSE、NDJSON）：在换行字节处切分，跨块的行和 UTF-8 字符都完整 |
| `res.cancel()` | 关闭（`http.close`） |
| `text()` / `json()` / `bytes()` | 读完整个流 |

限额：每个插件同时最多 8 个流；单个流至多 100 MiB；60 秒没人读就关闭；插件停止时全部关闭。权限、私有地址、重定向的
规则与普通 `fetch` 相同（检查发生在建立连接时）。

## 2. `providers`

### 清单

```json
"permissions": ["net:https://api.acme.example"],
"contributes": {
  "providers": [{
    "id": "acme",
    "name": { "zh": "Acme 云", "en": "Acme Cloud" },
    "icon": "cloud",
    "protocols": ["chat", "anthropic"],
    "models": [{ "id": "acme-large", "name": "Acme Large", "protocol": "chat", "context": 200000, "output": 8192 }],
    "signIn": { "flow": "signIn" }
  }]
}
```

- `models` 可以省略，改由代码的 `models()` 返回（启动和用户点“刷新模型”时调用）。
- `signIn.flow` 是一个 `ui.flows` 的 id（§4）；没有时账号只能由代码添加。

### 代码

```js
import { providers } from 'astra';

providers.register('acme', {
  // 每次发往上游之前（每个尝试一次）：返回地址、头、可选的新请求体。宿主发请求。
  async prepare(req, account) {
    const key = await account.secret();               // 这个账号的凭据（插件自己存的）
    return { url: 'https://api.acme.example/v1/chat/completions', headers: { authorization: `Bearer ${key}` } };
  },
  async models(account) { return [{ id: 'acme-large', protocol: 'chat' }]; },   // 可选
  async refresh(account, failed) { return 'renewed'; }, // 可选：上游 401/403 后调用；'renewed' | 'expired'；failed = { status, body（前 4 KB）}
  async usage(account) { return { used: 0.4, label: '40%' }; },                // 可选：宿主目前不调用它（没有消费方），返回形状未定
  transformResponse: { /* §2.2：上游回复不是网关认识的线格式时 */ },
});
```

- `req`：`{ provider（插件内的 provider id）, protocol, model（上游模型 id）, path, method, headers（已去掉凭据和传输类头）, body（JSON）, stream }`。
- 返回的 `url` 必须是 `net:` 权限覆盖的 https 源（开发插件的本机地址规则同 `fetch`）；返回的头不能改 `host`、
  `content-length` 等传输类头；返回 `body` 时替换请求体。`body` 可以是 JSON，也可以是 `Uint8Array`（protobuf、Connect
  帧等，boot 以 `bodyBase64` 传给宿主）；字节体的 content-type 取返回的头，没有时为 `application/octet-stream`。返回头里的
  内容类头（`content-type`）替换默认值，不会追加第二个值。
- 返回的 `state`（JSON 对象）是这次回复 §2.2 `ctx.state` 的初值：请求是怎么构造的（会话 id、序号）由此交给回复翻译。
- `prepare` 在宿主的请求路径上，时限 5 秒；它可以做宿主调用（读密钥、存储、刷新令牌时的 `http.fetch`）。

### 2.2 回复翻译（`reply` + `transformResponse`）

上游回复不是 chat / responses / anthropic / gemini 的线格式（Qoder 的 `{statusCodeValue, body}` SSE 信封、Cursor、Trae 的
自定义 SSE、Zed 的 NDJSON、Kiro 的 AWS 二进制事件流、Code Assist 的 `{"response": …}` 包装），或只需小修（Cline 的
`{data}` 解包、配额错误改成 429、工具名还原）时：宿主负责分帧，插件逐帧翻译，宿主再按线格式写出。

```json
"providers": [{ "id": "qoder", "protocols": ["chat"], "reply": { "framing": "sse", "output": "chat" } }]
```

- `reply.framing`：`sse` | `ndjson` | `json`（整个回复体一帧）| `aws-eventstream` | `connect`（Connect 流式协议）。`reply.output`：provider `protocols`
  之一，省略取第一个。`reply` 与 `transformResponse` 必须成对出现（SDK 的 `validate` 检查）；只有 `reply` 而代码没注册，
  请求以“声明了 reply 却没有 transformResponse”失败。
- **没有新权限**：它只改自己 provider 的回复，能连哪里仍由 `prepare` 返回地址的 `net:` 权限决定；插件拿到的也只是
  它自己请求的回复。

```js
providers.register('qoder', {
  prepare,
  transformResponse: {
    start(res, ctx) {                 // res = { status, headers, stream, body? }；非 2xx 时 body 是前 64 KB
      if (res.status === 402) return { error: { status: 429, message: '额度用完' } };   // 变成网关可见的失败
      // 也可返回 { status?, headers? } 覆盖状态和头
    },
    frame(f, ctx) {                   // 每个上游帧一次；返回 0 个、1 个或数组
      const inner = JSON.parse(f.json.body);                  // sse：{ event?, data, id?, json? }
      return { id: 'c1', object: 'chat.completion.chunk', model: ctx.request.model,
               choices: [{ index: 0, delta: { content: inner.text }, finish_reason: null }] };
    },
    end(ctx) { return { /* 收尾帧 */ }; },
    dispose(ctx) { /* 回复结束（正常、失败或客户端断开）：停掉定时器和旁路调用 */ },
  },
});
```

- `ctx = { request: { protocol, output, model, stream }, account: { key, secret() }, state }`；`state` 是每个回复一份的
  普通对象，`start` / 每个 `frame` / `end` / `dispose` 共用，初值是 `prepare` 返回的 `state` 的副本。
- `dispose(ctx)`：回复结束后宿主总会调用一次（`end` 之后，或失败、客户端断开时代替它），时限同样 2 秒。
- 帧形状：sse `{ event?, data, id?, json? }`（多行 `data` 以 `\n` 连接，按 HTML 规范处理注释与 CR/LF/CRLF；流在事件
  中间结束时，已到的数据仍交出）；ndjson 与 json `{ json }` 或不是 JSON 时 `{ text }`；aws-eventstream
  `{ headers: { ':event-type': … }, json | text, bytes? }`（先校验 prelude 与整条消息的 CRC32，失败即请求失败；
  `bytes` 是 base64，只在载荷不是 UTF-8 文本时给）；connect 每条消息是 1 字节 flags + 4 字节大端长度 + 载荷，
  数据消息为 `{ flags, bytes }`（base64，通常是 protobuf，由插件解码），结束消息（flag 0x02）为 `{ flags, end: true,
  json | text }`（Connect 的 JSON 尾部 `{ error?, metadata? }`），其后的字节不再读取；压缩消息（flag 0x01）使请求失败。
- 输出：**流式请求**（`ctx.request.stream`）里，每个输出对象宿主写成一个 SSE `data:` 事件并立即刷出；anthropic 写
  `{ event, data }` 对；字符串 `"[DONE]"` 原样写出（chat 输出在结束时宿主自己补 `data: [DONE]`）。**非流式请求**里
  宿主不写 SSE，插件在整个回复上必须恰好产出一个完整响应体对象（通常在 `end` 里，帧里先累积到 `state`）——上游是
  流而客户端要非流式（Qoder 总是流），就这样聚合；反过来上游是整包 JSON（`json` 帧）而客户端要流，就把它拆成输出
  帧。输出是流还是体，由客户端请求的 `stream` 决定，不由插件声明。
- 失败：`frame` / `end` 返回 `{ $error: { status, message } }`（不能用 `error`，那是合法的协议流错误块）——在第一个输出
  字节之前，回复变成该状态的失败；之后连接以错误中断。插件抛错、单次调用超过 2 秒、帧大于 8 MB、回复超过 256 MB、
  上游字节不符合声明的分帧：请求以 `HttpRequestException`（消息带插件 id）失败，故障转移照常；绝不会静默截断。
- 提前结束：`frame` 返回的输出里含 `{ $end: true }` 时，宿主写出同批其余输出，停止读取并关闭上游，再调 `end`。用于
  上游是双向流、回答完了连接仍开着等客户端的情况（Cursor 的 agent Run 在模型发出工具调用后就等工具结果）。
- 双向流：回复进行中客户端还要发消息时（Cursor 的 HTTP/1.1 走法：`RunSSE` 收、每条客户端消息一个 `BidiAppend`），
  插件在 `prepare` / `frame` 里自己用 `http.fetch` 发这些旁路请求（不必等待，它们在引擎里继续跑；心跳用 `setInterval`），
  在 `dispose` 里停掉。
- 不缓冲整个流：宿主一次只读一帧、调一次插件。第一个输出字节出来之前宿主会先读到足够的帧（所以首帧里的配额错误能变成真正的状态码）。
- 非 2xx 的上游回复也先交给 `start`（带 `body`）；它不返回 `error` 时，回复原样通过，由 `ProviderFailover` 按状态分类。

### 账号

`providers.accounts.list(provider)` / `add(provider, { key, displayName, email?, plan?, secret })` /
`update(provider, key, { … })` / `remove(provider, key)`。`secret` 存进插件的密钥（名字 `provider:<id>:<key>`），
`account.secret()` 读它。账号行是普通的 provider 账号（`kind = plugin`，`extra.plugin_key = key`），所以账号卡片、
冷却、故障转移、负载均衡都照旧。

### 宿主侧

- **行**：每个 provider 一行，id `plugin2-<插件 id>-<provider id>`（点换成 `-`），`AuthScheme = plugin`，
  `Settings.plugin = { v2: true, plugin, provider }`，端点 `plugin://v2.<插件 id>.<provider id>[/v1|/v1beta]`。
  v1 的同步只管 `plugin-` 开头的行，v2 的行由 `PluginV2ProviderSync` 维护：插件不在了就停用并标记 `absent`，
  从不删除（令牌池、绑定和历史请求还指着它）。
- **请求**：网关已经把 `AuthScheme = plugin` 的请求交给插件传输（`PluginFetchHandler`）。主机名以 `v2.` 开头的交给
  v2：取出 provider 和模型 → 插件的 `prepare` → 宿主按返回发请求（与 `fetch` 相同的私有地址检查）→ 响应流回
  流水线。清单没有 `reply` 块的 provider，响应原样流回（上游必须说 `protocols` 之一的线格式）；有 `reply` 块的，
  经 §2.2 逐帧翻译。只想改写已是网关格式的回复，仍用 `gateway.hooks`。
- **401 / 403**：流水线对插件 provider 调用刷新；v2 的刷新是插件的 `refresh`，返回 `expired` 时账号标为过期。

## 3. `clients`

```json
"contributes": {
  "clients": [{ "id": "acme-cli", "name": "Acme CLI", "config": "~/.acme/config.json", "format": "json",
                "model": "model", "prefix": "", "bin": "acme", "icon": "terminal" }]
}
```

```js
import { clients } from 'astra';
clients.register('acme-cli', { connect(input) { return { 'gateway.url': input.gateway.v1, 'gateway.key': input.gateway.key }; } });
```

- 描述与 v1 agent 插件相同，所以宿主把它当作一个 agent 描述（客户端 kind `plugin-<id>`）：写入仍全部经过
  `PluginClientAdapter` → `ClientConfigApplier`，备份、漂移检测、离线 `restore-all` 的不变量不变（`restore-all`
  只用记录的描述，不运行插件代码）。
- `connect(input)` 的输入输出与 v1 相同：`{ gateway: { url, v1, key }, model, models, agent: { id, config } }` →
  要写的键值。它在 `main` 上下文运行，时限 5 秒。
- 一个客户端 id 只能由一个插件提供；与 v1 agent 插件同名时 v1 优先，v2 那个报冲突。

## 4. `ui.flows`

分步流程（登录向导）。清单：`"ui.flows": [{ "id": "signIn", "view": "signInView", "title": "登录 Acme" }]`。
宿主在 Sheet 里打开这个视图（`surface = "sheet"`），`params` 里有 `{ flow, provider?, account? }`。视图用普通组件
画每一步（API key 表单、显示设备码和链接、粘贴授权码），完成时调用 `providers.accounts.add(...)` 再
`ctx.close({ ok: true })`。宿主在提供商页面的“添加账号”和账号卡片的“重新登录”里打开它。

设备码轮询之类的等待用 `timers.sleep` + `http.fetch`，在动作里 `ctx.flush()` 推送进度。

## 5. 权限

| 权限 | 允许什么 |
|---|---|
| `providers` | 注册 `providers` 扩展点、管理自己 provider 的账号 |
| `clients` | 注册 `clients` 扩展点 |
| `legacy.auth:import` | 从 v1 provider 插件升级时，一次性拿到那个 v1 插件自己在 `plugin-auth.json` 里的条目（`ctx.upgrade.from.auth`） |

`ui.flows` 用 `ui` 权限。

## 6. 从 v1 provider / agent 插件升级

- **provider**：v2 清单的 `replaces` 写 v1 包名，`providers` 里的 id 与 v1 的 provider id 相同时，升级把 v1 的行
  `plugin-<id>` 的令牌池、客户端绑定指向新行 `plugin2-…`（请求日志保留旧 id）。声明了 `legacy.auth:import` 的，
  宿主把 v1 的登录条目交给 `ctx.upgrade.from.auth`，插件写进自己的密钥并 `providers.accounts.add`。
- **agent**：kind 相同（`plugin-<id>`），客户端记录和已写入的键原样保留，不重新写用户的配置文件。
