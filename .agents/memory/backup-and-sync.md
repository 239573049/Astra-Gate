Whole-installation backup and sync work on **documents** (a config row with its child rows, a settings value, a client, a Skill), generated from `BackupCatalog.Specs` (`SELECT *` minus skipped columns), not from per-feature code. No migration: sync state is the settings key `backup_sync_state`.

**Why:** other agents add tables in parallel; a hand-written exporter would silently skip them. `BackupCatalogTests` makes an unclassified table or settings key a test failure at merge time. Secrets are DataProtection-bound to one machine, so they travel decrypted inside the AES-GCM envelope only (an unencrypted file cannot hold keys). magpie merges per *part* (providers / settings / library ...); the brief asked for per record, so `SyncMerger` is three-way per document with tombstones and last-writer-wins (a local change counts from when it was first seen, so an offline machine does not win by waking up late). Clients and Skills are written through their engines, never directly; `enabled` of a client is this machine's.
**How to apply:** a new table or settings key -> classify it, add a `TableSpec`, seed it in `BackupRestoreApiTests.SeedAsync`. A new machine-local field of `app` -> `AppMachineFields`. Not done on purpose: magpie's own-field memory ("kept on this computer" per agent field), `FollowServer`, undo of the last sync (the safety backup before a restore / first sync is the undo), usage sharing, WebDAV listing / PROPFIND (manual remote backups are `latest` + a timestamped copy), plugin installation on restore (a `plugins` row only updates an installed plugin; the rest is reported as not installed), library project paths and placements (machine-local). **Unverified:** live WebDAV / S3 / GitHub servers (only fake HTTP and AWS's published SigV4 vectors; the GitHub contents-API shapes are from its documentation), Windows paths, the Avalonia mirror on a real window, a sync of the library with large Skills (capped 16 MB per file / 32 MB per Skill; bigger ones are left out with a warning).
